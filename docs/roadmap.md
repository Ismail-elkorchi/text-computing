# Direction and acceptance criteria

The goal is useful, composable text work in TypeScript. Breadth is valuable when
the implementations share trustworthy contracts and their limitations are
measured.

## 1. Prove the unified library

Keep pack-free rules, classical classification, corpus analysis, search, and
data conversion working alongside resource-backed analysis. Gate direct versus
pipeline equivalence, document/graph/evidence serialization, cache identity,
module imports, and browser-compatible bundles. A new public module must not
create a second document or execution contract.

## 2. Turn construction primitives into evaluated solutions

Select representative applications and independently annotated evaluation data
before expanding task labels. Near-term candidates are contextual morphology
and tagging, dependency-based extraction, domain classification, and combined
corpus/search workflows. Compare lexical, rule/FST, classical, and neural
approaches where appropriate. Record quality by language, domain, text length,
and failure category alongside latency, memory, and distribution size.

The existing trainable sequence models and parser need usable resources and
held-out evaluation, not another API tier. The Arabic NER slice needs broader
evaluation and tokenizer/backend conformance before broader readiness claims.

## 3. Strengthen resources and operation

Extend Forge's reproducible resource contracts to the resources demanded by
those applications. Keep acquisitions explicit, licenses and checksums
auditable, and runtime identities reproducible. Expand actual browser/edge
inference coverage and resource lifecycle controls where a supported workflow
requires them.

## 4. Add deeper linguistic and semantic analysis

Constituency parsing, coreference, relation/event extraction, attribution,
semantic representations, and retrieval are candidates, not promises of
coverage. Prioritize them by application value and available evaluation, using
the same document, graph, processor, and resource contracts.

A feature is ready when it solves a defined workload with measured quality and
cost. A schema, dataset reader, or generic rule constructor alone is not that
feature.
